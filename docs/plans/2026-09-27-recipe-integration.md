## 二、四个发现

### 2.1 卡上有一个 `scene` 字段，没人消费

声明 `lib/characters/model.js:25,53`、映射 `lib/characters/formats.js:53,82,112,143`、导出 `lib/characters/transfer.js:355`——三处齐，`lib/` 再无读取点。（`media/prompt.js:44` 里的局部变量 `scene` 是从 `scenario` 派生的，同名巧合。）

**决定：按历史残留处理，不复用、不指望。P2 不依赖它。**

### 2.2 导进来的卡，有一半字段是白写的

`mes_example` 与 `post_history_instructions` **默认不进 prompt**——`DEFAULT_BLOCKS` 只有 7 块，没有 examples 块。无条件下每轮真正生效的只有 `name / description / personality / scenario / system_prompt`；`first_mes` 只在建对话时用一次。

### 2.3 `character_book` 的壳在，消费端不在

导入链路完整，但它只进 lore 库当设定文本，**不作为「角色设定图集」存在**。

### 2.4 立绘 ≠ 设定图

`saveAvatar` / `POST /media/portrait` 只写一个 `avatar` 字段——**一张**卡一张头像。Mozi 说的「角色设定图」在 galgame 语境里通常指**多张**（换装、表情差分、正侧背三视）。

结论：设定图这条线不是「有一半」，是**还没有**。立绘链路的价值在于它证明了「App 能出图、能落盘、能显示」，那是地基，不是成品。

### 3.2 导演层 · 剧情公式（v2 重写）

#### 它是什么

**不是剧本，也不是节拍清单，是一组状态约束。**

v1 的错误在于：把「公式」理解成「每一拍写什么」。那样骨架仍被预先写死，模型只是填字。v2 的定义是——

> 公式规定**在什么条件下必须发生什么性质的事**，不规定**具体发生什么**。
> 每轮发生什么，由模型自己决定。

举例：`张力每轮 +1`、`张力 ≥ 7 时必须出现一次正面冲突`、`张力 ≥ 10 时触发一次不可逆事件并回落`。模型永远拿到的是「现在的状态 + 约束」，而不是「本轮请执行第 2 拍」。

#### 数据模型

```json
{
  "id": "act-3", "name": "三幕剧", "characterId": "…",
  "state": {
    "tension": { "init": 1, "min": 0, "max": 10 },
    "turn":    { "init": 0 }
  },
  "rules": [
    { "when": "always",        "effect": "tension += 1" },
    { "when": "tension >= 7",  "effect": "tension -= 3", "brief": "必须出现一次正面冲突" },
    { "when": "tension >= 10", "effect": "tension = 2",  "brief": "触发一次不可逆事件" }
  ],
  "freeform": "本轮发生什么由你决定——不要按清单走，只遵守上面的约束。"
}
```

**没有 `beats`。** 这是 v1 与 v2 的分水岭。

#### 每轮注入的形态

动态尾部多一块：

```
【导演 · 本轮】
张力 5/10（上一轮的摩擦没解）
约束：到 7 必须出现一次正面冲突；到 10 触发不可逆事件。
本轮发生什么，你决定——不要按清单走。
```

#### 模型自决的接口

光有规则还不够：模型得能**推动状态**，否则它只能自由发挥文字，状态照旧死着。

所以给一个**可选的上报语法**，跟 `[场景]` 标记同族：

```
[状态 tension+2 flag:confessed]
```

规则层负责**校验并应用**：数值不许越界、flag 不许凭空造、非法上报丢弃并在 trace 里记一笔。模型不上报也不报错——基线漂移（`always: tension += 1`）保证剧情往前走。

**这一层是「模型自决」与「可控」的交界**：方向由规则给，事件由模型给，合法性由规则层兜。

#### 与预设系统的关系（v1 漏掉的前提）

`DEFAULT_BLOCKS` 里的 `POST_HISTORY`（收尾指令）与导演块语义高度重叠——都是「告诉模型下一句怎么说」。

**定义**：导演块排在 `postHistory` **之后**（更靠近本轮），并在自己的文本里显式声明硬约束身份。若用户预设的 postHistory 与之冲突，**导演块说明自己覆盖**——这句话要写进注入文本里，而不是靠模型猜。同开时在 trace 里留一条记录，供排查。

#### 计数口径（v1 漏掉的前提）

`turn` 的定义：**一个用户回合 = 一次完整生成**。不是消息条数，不是发言人数。

群聊里一次生成可能产出多条消息、多个发言者、以及私语——**仍然只算一轮**。这条必须写死，否则 `tension` 的增速在群聊和单聊里完全不同。

#### 变量命名空间（v1 漏掉的前提）

导演变量统一用 `__dir.` 双下划线前缀，理由两条：

1. 用户自定义变量几乎不可能撞上双下划线；
2. **禁止在角色卡字段里引用导演变量**。`CHARACTER_MACRO_FIELDS`（`description / personality / scenario / first_mes / mes_example / system_prompt / post_history_instructions`）**全部落在稳定前缀里**——在这里写 `{{__dir.tension}}`，每推进一次就让整段前缀缓存作废。这条禁令必须写在 spec 里，不能只靠自觉。

#### 状态归属：实体是配置，状态是会话的

导演实体（规则集）是**纯配置**，存在 `<dataDir>/director/<id>.json`；运行状态存在**该场对话的 variables** 里。

于是同一张卡开两场对话 → 两场各自演化，互不覆盖。这不是缺陷，是正确行为：**同一个剧本，两次不同的演出**。

推论（P3 打包要用）：配方导出的是**实体（规则）**，不含进度。进度属于会话，不进配方。

## 四、不变式（v2 修正）

1. **不新造世界观机制**：lore 已是完整的一套，导演层只消费它。
2. **只往动态尾部插一块，不重排既有顺序。**
   —— 但**不等于零影响**：尾部多一个每轮变化的块，会经 `estimateTokens` 计入 `systemTokens`，进而挤压 `historyBudget`（`pipeline.js:764-766`）；`audit.included` 也会多一项。这是已知代价，明写，不粉饰。
3. **不做破坏性的卡格式变更**：导演实体独立于卡，旧卡照常解析。
4. **导演层默认关**：与场景插图同一条纪律。
5. **禁令**：角色卡字段内不得引用 `__dir.*`（见 §3.2 命名空间）。
