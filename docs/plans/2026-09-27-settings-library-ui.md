# 设定库 · UI 重设计落地方案

- 日期：2026-09-27
- 方案：奥菲莉娅
- 决策：月曦夜
- 状态：**待落地**

## 一、背景

设定库（`#drawer-settings`）是 ElecKoi 里条数最多的一个面：真库 **106 条**，而抽屉只有 **344px** 宽（`--ctx-w`）。

现在的卡片是"甲"形态——四行：标题＋开关 / 触发词 / 归属 / 正文折叠＋操作。**这个形态保留**（用户明确要甲）。

问题不在密度，在**秩序**：106 条平铺，滚约 11,900px，永远不知道自己在哪、也回不去。

## 二、真库实测（不是估计）

```
总条数        106
trigger.type  always 64 · regex 40 · keyword 2
priority      106 条全是 100   ← 导入默认值，从来没用过
order         1..106 全唯一     ← 这才是真正的顺序
enabled       全 true
position      before_char 82 · after_char 22 · 0/1 各 1
anchor        只有 2 条有值
createdAt / updatedAt  全有
```

**分类字段不存在。** 用户要的「角色 / 物品 / 设定」这类维度，数据里没有。

## 三、一个必须先修的矛盾

`priority` 在引擎里真的在用，但**三处说法不一致**：

| 位置 | 写法 | 方向 |
|---|---|---|
| `lib/lore/budget.js:44` | `-Number(entry?.priority ?? 0)` | **大的先** |
| `lib/lore/matcher.js:561` | `-Number(ea.priority ?? 0)` | **大的先** |
| `lib/settings/model.js:208` | `a.priority - b.priority` | **小的先** |
| `lib/settings/model.js:45` | 注释「数字越小越优先」 | 第三种说法 |

`budget.js` 抄的是 DiceFrame `entry_sort_key`（priority 降序）。**以它为准。**

**落地第一件事：把 `model.js` 的排序改成降序，注释改对。**

## 四、方案

### 卡片：保持甲（四行）

```
┌──────────────────────────────┐
│ 名字                     [开关]│
│ 触发词（只在触发组画）           │
│ [本卡] [分类] [常用度]           │
│ ▸ 正文          编辑 删除(hover)│
└──────────────────────────────┘
```

**唯一对甲的改动**：编辑 / 删除改成 hover 才出——106 张卡每张常驻两个按钮，比内容还显眼。

### 要加的八件

**1. 分页（10 条/页）**
- 吸底：`‹  2 / 11  ›`，右侧显示当前范围条数
- 分页切的是**卡片**；抬头跟着出现或消失
- **折叠的组不参与分页**（收起「常驻」，页码从 11 变 4）

**2. 分组维度可切换**

抬头那层能在三个维度间切，不做成二选一：

| 维度 | 回答的问题 |
|---|---|
| 生效方式 | 常驻 / 触发 —— **它什么时候进上下文** |
| 分类 | 角色 / 组织 / … —— **这是什么东西** |
| 常用度 | 核心 / 常用 / 冷门 / 未标 |

**3. 折叠**
- 点抬头收起 / 展开
- 状态存 `localStorage`（它不是临时视图，是"我平时只看哪一组"）
- key 要带维度：`eleckoi:settings-folded:<维度>:<组名>`

**4. 排序**

组内生效，分组不动。四种：`原始顺序（order） / 名字 / 分类 / 最近修改`

**5. 优先级 = 常用度，三档**

用户口径："哪些是世界观最常用的，哪些是只用几次的"

| 档 | 值 | 含义 |
|---|---|---|
| 核心 | 300 | 世界观骨架，预算不够时优先占位 |
| 常用 | 200 | |
| 冷门 / 未标 | 100 | **现状值**——不标就一个字不变 |

- 卡片上点徽章改（小浮层选三档）
- **只在非 100 时画徽章**（否则 106 个「100」是墙纸）
- 复用 `priority` 字段，**真的影响上下文取舍**（这是用户选 A 的原因）

**成本已核实**：
- **不膨胀**：`applyBudget` 是硬上限（`used + cost <= budget`，放不下跳过继续试），换 priority 只换「谁进来」，不换「进来多少」
- **不伤缓存**：`pipeline.js` 已按缓存稳定性分拣（常驻 → 静态前缀，关键词激活 → 动态尾部）。priority 是**稳定值**，"改"是**事件**不是常态，不会引入逐轮抖动。改一条之后那一次前缀 cache miss，之后恢复。

**6. 分类**

- 设定对象上新增 `category` 字段
- 类目表存 `app-data/eleckoi-tavern/categories.json`
- **默认 8 个**：`角色 / 组织 / 地点 / 物品 / 能力 / 事件 / 设定 / 系统`
  - 比用户举的三个多：「能力」（交感同操、霜语血脉）和「事件」（第三章-旧宇宙港防卫）在真实数据里各有一批，塞进「设定」会让兜底桶又变大
- **可增 / 删 / 改名 / 并到…**（"并到"比"删除"诚实：删了条目掉进未分类，并了它们还知道去哪）
- **自动初判只填高置信的三类**（组织 / 系统 / 地点）：

  | | 实测 |
  |---|---|
  | 准的 | 组织 8、系统 13、地点 6（靠「企业」「[xxx]」「塔/星/港」） |
  | 漏的 | 角色只认出 14/27——`拉斯提/男性原版`、`莉娜·许奈德` 全进了「设定」 |
  | 兜底 | 「设定」桶 55 条——**兜底桶一大，分类就等于没分** |

  所以：**自动只填有把握的，其余留「未分类」**。宁可空着让用户自己分，也不要猜错一百条让他回头改。

- 已有 106 条：**加一个「自动分类」按钮**，点了跑一次启发式填高置信的，其余留空
- **导出 ST 时 `category` 不带出去**——它是本地标签，不是世界书的一部分，绝不能反过来要求模型输出什么

**7. 批量选择**

- 卡片左侧勾选槽**一直占位（26px）**，只是没悬停 / 没选中时透明——不然勾选一出现，整列卡片宽度会跳
- 选中后顶部出现操作条：`已选 N 条 · 设为 [类目▾] · 应用 · 取消`
- **这是清空「未分类」的主力**：55 条一条条点没人受得了

**8. 类目管理弹层**

- 标题栏一个「类目」按钮打开
- 每行：类目名 + 当前条数 + 改名 / 并到… / 删除
- 底部一个添加输入框
- **用正经输入框，不要 `prompt()`**（样张里用 `prompt` 只是示意）

## 七、不做的

- **不动卡片形态**（用户要甲）
- **不动引擎的其他部分**（只改那一处方向矛盾）
- **不动别的抽屉**（那是下一块）
- **不做拖拽排序**（order 字段够用，拖拽是另一个工程）
