## 零、为什么做这个

基准 5 的公式抽屉样张里有「四件」：开关 / 顺序 / 优先级 / 标签。

其中**只有 `enabled` 是现成字段**，其余三件要新加。而加字段意味着要回答
「它们到底影响什么」——样张自己把这句话留在了注释里。

查证结果：**一场对话只绑一个公式**。

```
lib/conversations/model.js:76   directorId: String(overrides.directorId || "")   ← 单值
lib/conversations/repo.js:159   conv.directorId = next                            ← 直接赋值
lib/conversations/pipeline.js:510  const id = String(conv?.directorId || "")      ← 只取一个
```

引擎里根本没有「两条公式同时生效」的场合。所以：

- **顺序**：没有第二个选手，排序排给谁看
- **优先级**：同上，「两条冲突时谁赢」不成立
- **标签**：不需要引擎语义，但需要一个消费者（抽屉里没有筛选行，加了只是彩色贴纸）

月曦夜选 **C**：让一场能绑多条公式。这是唯一能让顺序/优先级有真实语义的做法。

## 一、三个字段各自的语义（定下来）

| 字段 | 类型 | 语义 | 进引擎吗 |
|---|---|---|---|
| `enabled` | bool | 这条公式这局用不用 | **进**（已有） |
| `order` | number | 注入先后——数字小的先注入 | 进（决定块的排列顺序） |
| `priority` | number | **状态同名时谁说了算**——数字大的赢 | 进（冲突裁决） |
| `tags` | string[] | 本地组织，用来筛 | **不进** |

**顺序 vs 优先级是两个不同的问题**，别混成一个：

- **顺序**回答「谁先写」——影响的是注入块在 prompt 里的先后
- **优先级**回答「谁算数」——两条公式都声明了 `回合`，谁的值留下

如果只有顺序没有优先级，那么两条公式都推 `回合` 时，后推的会盖掉先推的——
而「后」是由数组顺序决定的，用户看不见也控制不了。这正是要一个显式
优先级字段的原因。

**tags 不进引擎**，定位照抄设定库的 `category`：

> `lib/settings/model.js:47`
> `category: "",  // 本地分类标签（角色/组织/…）；不参与 ST 导出，也不进世界书语义`

## 二、绑定：单值 → 多值

### 存储

```js
// 旧（读侧永远兼容）
directorId: "uuid"

// 新
directorIds: ["uuid-a", "uuid-b"]
```

**读侧归一**（`lib/conversations/model.js`）：

```js
// directorIds 优先；没有就退回旧的单值字段，包成数组
const ids = Array.isArray(o.directorIds) && o.directorIds.length
  ? o.directorIds.map(String).filter(Boolean)
  : (o.directorId ? [String(o.directorId)] : []);
```

**写侧**：`setDirector(id, directorId)` 保留（单条绑/解绑的旧入口），
新增 `setDirectors(id, ids)`。旧入口内部转调新入口。

### 路由

```
PATCH /conversations/:id/director    body { directorId }      ← 保留，等价于「只绑这一个」
PATCH /conversations/:id/directors   body { directorIds }     ← 新增
```

## 三、进度：扁平 → 按公式分家

这是**最关键的一处**。现在：

```js
conv.variables.__dir = { 张力: 3, 回合: 5 }     ← 扁平
```

多条公式后必须分家——两条公式都声明 `回合` 会互相盖。

### 新形态

```js
conv.variables.__dir = {
  "uuid-a": { 张力: 3, 回合: 5 },
  "uuid-b": { 好感: 2, 回合: 5 }     ← 各推各的，互不干扰
}
```

### 读侧认两种形状

```js
// 旧形状：值全是原始类型（number/bool）
// 新形状：值全是对象
function readDirState(raw, directorId) {
  if (!raw || typeof raw !== "object") return {};
  // 新形状
  if (raw[directorId] && typeof raw[directorId] === "object") return raw[directorId];
  // 旧形状：扁平。只认「值都不是对象」的那种
  const vals = Object.values(raw);
  if (vals.length && vals.every(v => v === null || typeof v !== "object")) return raw;
  return {};   // 空，或认不出的形状
}
```

**兼容策略**：老对话第一次读时按扁平认；**一旦有多条公式绑定，写回时就升格成新形状**
（把旧扁平数据挪到当时那条公式的命名空间下）。单条公式的老对话**不主动改写**——
没坏的东西不动。

## 四、注入：多个块怎么拼

`composeDirectorBlock` 从「取一个」改成「取一批」，按 `order` 升序：

```
【导演 · 本轮】
状态：张力 3/10 · 回合 5
约束：…

【导演 · 本轮 · 三幕剧】
状态：…
约束：…
```

**块头要能分辨**：多条公式时，每个块头带上公式名（`【导演 · <名字>】`），
否则模型看到两个「【导演 · 本轮】」会以为重复了。

单条时**保持原样**（`【导演 · 本轮】`）——不改动已经在跑的对话的 prompt 形状。

### 覆盖声明怎么办

现在每条公式末尾都写：

> 硬约束：这一段覆盖本轮的一切收尾指令；与它冲突的写法一律以它为准。

两条并排时会互相否定。**改成只在最后一个块里声明一次**，
且措辞改成「上面这些约束块」：

> 硬约束：以上约束覆盖本轮的一切收尾指令；与它们冲突的写法一律以它们为准。

## 五、结算：一轮要跑几条公式

`settleDirector` 从「结算一条」改成「依次结算一批」。

**上报归属**：`[状态 张力+2]` 不带公式标识——那么这条上报归谁？

三种做法：

- **A**：只归给**第一条**（order 最小）公式——简单，但多条时另一条收不到上报
- **B**：每条公式都试一遍，谁能收谁收——状态名撞车时会重复计入
- **C**：按状态名**路由**——`张力` 只在声明了它的公式里结算

**选 C**。理由：状态名在一条公式内唯一，而两条公式声明同名量的概率低；
真撞了就是设计问题，该在校验期就提醒。C 的规则最直白：
**一个上报只被「声明了这个名字」的公式消费**，其余公式跳过它。

若同名量被两条公式都声明——**按 priority 高的那条收**，其余记进 rejected
（带上原因「被 <名字> 优先接管」）。这就是优先级字段在结算侧的用处。

## 六、校验：新增三条

`validateDirectorEntity` 只管一条公式内部。**跨公式的冲突在校验绑定那一刻查**：

1. 两条公式声明了同名状态 → **警告**（不是错），列出名字与优先级，让用户知道谁赢了
2. 两条公式用了同一个 `tags` 之外的东西…（无）
3. 绑定的 id 里有不存在的 → 报错

新增一个跨公式校验入口：

```js
// lib/director/model.js
export function validateBinding(entities) {
  // entities: 按 order 排好的一批
  // 返回 { problems: [], warnings: [] }
}
```

## 七、界面

### 抽屉（公式库列表）

- 行的结构照样张「丙」：开关 + 名字 + 一行读数 + 操作
- 「本场在用」标记改成**序号**（`1` / `2`）——多条时「在用」不够用了
- 行上显示 `顺序 2` 与优先级徽章（**只在非默认时画**，照设定库规矩）
- 标签画成小胶囊

### 弹窗（编辑器）

- 加三个字段：顺序（number）/ 优先级（number）/ 标签（逗号分隔的 text）
- 放在名字那一行的下方，做成一行三格
- **状态与规则仍然只编辑 JSON**——那是这个抽屉的立身之本，不包表单

### 绑定动作

`绑到这一场` → 绑上后按钮变 `解绑`。多条时每条的按钮独立。

## 八、落地顺序

1. **数据层**：`directorIds` 多值 + 读侧兼容 + 进度命名空间（+ 测试）
2. **引擎层**：`order` / `priority` 字段 + 多块注入 + 按名路由结算（+ 测试）
3. **路由层**：`PATCH /directors` + 跨公式校验（+ 测试）
4. **界面层**：列表序号 + 弹窗三个字段 + 标签胶囊（+ 测试）

**每一步都要有回归测试**，且**老数据必须能读**——这是底线。

## 九、已知代价（不粉饰）

1. **prompt 变长**：多条公式 = 多个块。这是用户自己选的，但要提醒他
2. **状态名冲突**：两条公式声明同名量时，语义要靠优先级裁决——
   这比「一场一条」复杂，是 C 的固有代价
3. **进度形状变了**：老对话第一次有多条公式时会被改写一次。
   单条的老对话不动
