# 场景插图 · 规格（Scene Illustration Spec）

> 版本：v1 · 落地于 2026-09-27 · 与 `docs/plans/2026-09-25-scene-illustration-and-gallery.md` 的 2.1–2.4 对应

这份文档只做一件事：把「什么触发出图、什么不算」说清楚。
它**不是**执行手册——执行手册在计划里；这份规格是给代码看的契约，
改动这里就等于改契约，改代码前先改这里。

---

## 1. 场景标记的语法

模型在回复**末尾**输出一个可选的 `[场景]` 块。有块就出图，没有块就什么都不做。

```
[场景] 一段自然语言的画面描述，1–200 汉字以内。
```

规则：
- 单行。描述不能跨行；跨行的部分**不属于**这块。
- 方括号是**半角**：代码里 `SCENE_MARKER_HEAD` 就是 `[场景]` 这四个字符。
  全角 `［场景］` 与英文 `[Scene]` 都不算标记（写错了就说错了）。

  > **2026-09-27 修正**：这一行原文写的是「**全角**方括号是硬要求」，
  > 而代码里的 HEAD 是**半角**（`[` = U+005B、`]` = U+005D）。文档与代码对不上——
  > 而这一轮要往提示词里注入一句“该怎么写标记”的指令，照文档写就会写出一个**永不生效**的指令。
  > 以代码为准修了这句（代码是跑的那个）。
- 描述前后可以有空格，写进代码时会被 trim。
- 描述为空（`[场景]` 后面没有内容）视为无标记。

### 1.1 位置

- 出现在**最末**一行；中间穿插的 `[场景]` 不识别。
- 允许前面留一段尾随空白（换行/空格）。
- 标记**不是**回复正文的一部分——被剥离之后剩下的才是用户看到的正文。

### 1.2 多标记

模型偶尔会连写两块（写完场景又后悔，改口补一句）。
处理规则：**只取第一块**，其余的静默丢弃。

不做成报错的原因：报错会污染 UI，而多写的其实是被丢弃的冗余，
不是错误；用户能感知到的应该只有一句"按第一块画了"。

### 1.3 带换行

`[场景]` 后跟 `\n` 是"标记里带换行"的典型形态。
处理：**只取紧邻 `[场景]` 的同一行文本**，换行之后的所有行都不算描述。

这条比"取整个块直到下一个空行"更严，因为：
- 模型经常在下一行开始继续写正文，把那些算进来就成了"正文被画成图"；
- 单行描述足够说清"这一幕的画面"，跨行的通常意味着模型没想好，
  那不如当作没有。

### 1.4 带宏

描述里可能出现 `{{char}}` / `{{user}}` / `{{bot}}` 这类宏。
处理：**原样存进消息的 prompt 字段**，不展开。

原因：宏展开发生在发送前，那时才确定"她是谁、他叫什么"；
提前展开等于把宏语义钉死在一次调用上，未来模型换了名字，历史插图里的
prompt 就变成错的。台账里存的是"当初模型写了什么"，不是"当时展开成什么"。

## 2. 谁消费这个标记

- **`lib/illustration/scene-marker.js`** —— 抽取与剥离。纯函数，
  输入回复正文，输出 `{ text, marker?, extras?, prompt? }`。
- **`lib/illustration/prompt.js`** —— 拼接出图提示词。输入卡字段 +
  场景描述 + 说话人，输出提示词字符串。
- **`lib/illustration/service.js`**（后续批次）—— 消费上面的产物去调出图。

上游（模型）与下游（出图）之间只有一层薄薄的翻译，
翻译规则都在这份规格里，不在代码里散落。

---

## 3. 什么时候出、什么时候不出

| 情况 | 行为 |
|---|---|
| 回复里没有 `[场景]` | **什么都不做**，不报错、不提示、不写台账 |
| `[场景]` 语法错（英文括号、跨行到空行之外） | 同上——当作没有 |
| `[场景]` 后面描述为空 | 同上——当作没有 |
| 语法对但描述只有标点/表情 | 视作有描述，交给出图引擎去判 |
| 同一回复里出现多个标记 | 只取第一块，其他丢弃 |

**核心纪律**：出图是**追加**的动作，不是**必要**的动作。
默认关（配置项 `scene.enabled=false`）时，即使标记正确也不出图——
用户没开就没有，不商量。

## 4. 模型漏写标记怎么办

**不救**。理由：

1. 提示词约束模型是**建议**，不是强制；每次回复都硬逼模型写 `[场景]`
   等于让它多写一次无用功，token 白烧。
2. 用户想补一张，有手动入口（`POST /conversations/:id/illustrate`，第 2.6 条）；
   兜底路径永远存在，不需要用"每句都写"来保证覆盖。
3. 默认关本身就是为了省钱省显存。

**这条写进 spec 的原因**：以后有人会说"这里模型漏了"当成 bug 报，
看这份文档就能一句话挡回去——这是设计，不是漏。

---

## 5. 写错标记怎么办

写错就是没写。规则见 §3。

唯一例外：如果用户在手动入口里显式给了描述，而描述里带 `[场景]`，
说明用户是想写描述不是想触发标记——手动入口不解析标记，直接把
整段当描述用。

## 6. 数据落点

一条插图对应：

1. **消息**：对话里多一条 `role="assistant" kind="illustration"` 的消息，
   字段 `{ mediaId, prompt, status }`。`status` 三态：`pending` / `ok` / `failed`。
   失败原因写在 `status` 的伴生字段 `failReason`（第 2.5 条会补全）。
2. **媒体台账**：`<dataDir>/media-index.json` 里多一条 `kind="scene"` 的记录，
   `id` 就是消息的 `mediaId`。`file` 是绝对路径，指向 `<dataDir>/media/…`。
3. **文件本体**：`<dataDir>/media/<mediaId>.png`。

**三处对得上**才算完成：消息指台账，台账指文件。任何一处失联，
UI 就该说清是"生成中"还是"文件已删"还是"这条记录本身没了"。

### 6.1 分类键（图库那两级靠它们）

台账的四个键就是**分类键**，已在 `lib/media/index-store.js` 的 schema 里定死：

| 键 | 值域 | 归谁 | 备注 |
|---|---|---|---|
| `kind` | `portrait` / `scene` / `reference` / `import` | 图的种类 | 立绘有卡无场；场景插图两者都有 |
| `characterId` | 角色卡 id | 图上是谁 | 立绘必有；场景插图有（带参考图那张） |
| `conversationId` | 对话 id | 图是哪一场的 | **场景插图才有**；立绘为 null |
| `createdAt` | ISO 时间 | 什么时候 | 两者都有，排序用 |

**这条不对称是设计，不是待补的洞**：立绘属于**角色卡**，场景插图属于
**一场对话**。所以「本场」这一级天然筛不出立绘——`conversationId` 是 null。
图库的空态会把这句话说出来（见 6.2），不让用户以为图库坏了。

### 6.2 图库的两级范围

界面：`ui/assets/modules/gallery.js` + 纯契约 `ui/assets/modules/gallery-query.js`。

| 级 | 查询 | 含什么 |
|---|---|---|
| **本场** | `/media/index?conversationId=<当前对话>` | 只这一场画出来的场景插图 |
| **全部** | `/media/index`（不带 conversationId） | 立绘 + 所有场次的场景插图 |

两条边界，都不是洁癖：

- **没开会话时不拼 `conversationId=`**。空串会被后端 `!= null` 当成一个
  真实 id 去比，结果恒为空——而那正是用户最不该看到的一种空。
- **`kind` 只在有值时拼**。同理，空 kind 会让后端一条都筛不出来。

对应测试：`test/regression-gallery-query.mjs`（13 条，含反证）、
`test/regression-gallery-drawer.mjs`（45 条接线）。

### 6.3 去重

App 这一侧**不做归档清单、不推送**（`docs/notes-gallery-intake.md` 定的）：
插图落盘到 `<dataDir>/generated/`，图库自己扫盘发现。

去重分两层，各管一段：

- **台账内**：`index-store` 的 `insert` 同 id 报错、`upsert` 同 id 覆盖。
  场景插图的 `status` 从 pending 走到 ok/failed 就靠 upsert 推进，
  不然同一条媒体会在台账里堆两行。
- **图库内**：按文件字节 sha256（`images.file_hash` UNIQUE）。
  与「引用了哪条台账」无关——Tavern 不需要为实现去重改 schema。

## 7. 上下文参与

**不参与。** 插图消息不进下一轮对话的 prompt。

写在这里避免以后当成 bug：有人会用"为什么模型看不见上一张"来质疑
这条，回答是"设计上就没有"。

想参与的话，走 `lib/llm/history.js` 的另一条路——把插图描述作为
`user message` 前缀追加，而不是让 illustration 消息直接进上下文。
这条路留给未来的场景，这一版不做。
