# 自动创建角色卡与世界书 · 设计

日期：2026-09-25
作者：奥菲莉娅（月曦夜的助手）
状态：设计已过三节审查（流程 / 生成端 / 审查界面），待用户复核书面规格

## 一、目标

用户说一句「我要一个 X」，App **联网检索可信来源** → 生成**符合原酒馆格式**的
角色卡 + 世界书（**成套**）→ **经人审查后**写进卡库。

## 二、非目标（YAGNI，v1 明确不做）

1. **不做从对话或文档反推**（那是另一条路：把已发生的内容沉淀成资产）。
2. **不做自动入库**。生成的东西必须先给人过一眼——生成很快，但"不像"就是垃圾。
3. **不做对话式反复打磨**（"再改改语气"这类）。v1 = 单次生成 + 手动改。

## 三、流程

```
用户说「我要一个 X」+ 可选（题材 / 语气 / 要不要世界书）
      ↓
① 检索    App 走白名单抓正文；抓不到或不够 → 提示「让我来查」（Agent 兜底）
      ↓
② 抽取    抓到正文 ──→ 事实清单 [{ fact, source{url,title,tier} }]
          纪律：只许抽取，不许新增；挂不上出处的直接丢
      ↓
③ 生成    事实清单 ──→ { card: ST V2 字段, book: character_book }
          ⚠️ 喂的是**清单**不是原文 —— 这道墙就是防幻觉用的
      ↓
④ 审查    逐条看内容 ← 来源 · 角色卡预览（像不像、开场白能不能用）
      ↓
⑤ 落盘    走现成的 formats / import 路写进卡库
```

## 四、三条关键决定（已获用户批准）

1. **出处跟着内容走** —— 每条事实必须挂来源，**挂不上就丢弃**（fail closed）。
2. **来源标类型** —— 百科 / 官方 / 社区 wiki 三类分开标，让人自己判断，
   而不是我们替他判"可信不可信"。（写 ACGN / 游戏世界时，社区 wiki 才是主力。）
3. **审查不可省** —— 自动生成的不直接进库。

## 五、数据契约

**事实清单**（抽取的输出，组装的输入）：

```json
[{ "fact": "……", "source": { "url": "https://…", "title": "…", "tier": "encyclopedia|official|community" } }]
```

**生成结果**：

```json
{
  "card": { "name": "", "description": "", "personality": "", "scenario": "",
            "first_mes": "", "mes_example": "", "creator_notes": "", "tags": [] },
  "book": { "entries": [{ "keys": [], "content": "", "position": "before_char" }] }
}
```

- **卡字段只用白名单里的那八个 + `character_book`**。
  原酒馆的其他内部字段一律不碰 —— 「角色卡内部字段不改，要兼容原酒馆的角色卡」是铁律。
- 世界书条目：`keys`（触发词）从事实里出；`content` 只写事实里有的；位置默认 `before_char`。
- 落盘时走 `lib/characters/formats.js` 现成的读写（ST 卡 V2：`spec: "chara_card_v2"`）。

## 六、来源与白名单

出网走 `sdk.network.fetch`（App 的原始 fetch 被 AppHost 的 Node 权限模型拒掉），
manifest 的 `network.allowedHosts` 逐个列域名。白名单支持 `*.suffix` 通配。

**来源可用性实测（2026-09-25，本机普通进程）：**

| 站点 | 结果 | 处置 |
|---|---|---|
| 萌娘百科 `zh.moegirl.org.cn` | **200** | 用 |
| arXiv `arxiv.org` | **200** | 用 |
| 灰机 wiki `www.huijiwiki.com` | 403 | 待复测（可能只拦首页） |
| 维基百科 `zh.wikipedia.org` | 连接超时 | 留名 + 标"需代理/兜底" |
| Fandom `*.fandom.com` | 连接超时 | 留名 + 标"需代理/兜底" |

⚠️ **上面测的是普通进程**。酒馆出网**走宿主**（跨 IPC），宿主若配了**出站代理**，
维基 / Fandom 可能是通的。所以设计里带一条机制而不是一张死名单：

> **来源可用性检查**：功能自带一次体检（逐域名打一次），
> 把不通的标出来，并告诉用户"这条要代理、或要走兜底"。

## 七、模型调用

**调用一 · 抽取**

- 输入：抓到的正文（按预算截断）+ 用户的一句话需求
- 输出：事实清单 JSON（每条必带 source）
- 纪律（沿用「前情提要」那套）：只许压缩抽取、不许新增、不许编；说不清就丢

**调用二 · 组装**

- 输入：**事实清单**（不是原文）
- 输出：`{ card, book }`
- 喂清单不喂原文，是这一节唯一的设计要点：模型没有自由发挥的原料

**第三道 · 出处核对**

- 生成结果里每个断言，都要能在事实清单里找到；**找不到的删掉**（不是改写）。
- 报告里写"删了 N 条越界内容" —— 把幻觉变成一个**看得见的数字**。

**解析失败不重试**：严格解析，失败就说清哪一条不合法（别让错的东西静默通过）。

## 八、审查界面

照 App 里已有的**导入预览**做（逐条 + 标记 + 可弃），不发明新形态。

```
入口：角色卡页 → 「AI 生成」（跟"新建"并排）
  ① 需求   一句话 + 可选（题材 / 语气 / 要不要世界书）
  ② 过程   检索了哪些站（域名 + 状态 + 抓到几条）· 事实清单（每条挂来源）
  ③ 结果   角色卡预览（名字 / 描述 / 开场白） + 世界书条目（逐条 留 / 删 / 改）
  底部：写进卡库 · 存成草稿 · 丢掉
```

- 每条事实、每条条目旁边挂来源（域名 + 可点开的 URL）
- 逐条可删可改，不是"全要或全不要"

## 九、任务与进度

长任务（检索 + 两次模型调用）走**提交 + 轮询**（照图库那套）。
这样**不需要新增能力**（`app/tasks.manage` 之类），也就少一次权限复核。

## 十、错误处理

| 情形 | 行为 |
|---|---|
| 检索 0 条 | 说清"白名单里没找到"，并提示可走 Agent 兜底 |
| 抽取解析失败 | 报哪一条不合法；**不重试** |
| 组装越界 | 删掉并计数，报告里写清删了几条 |
| 来源不可用 | 可用性检查先跑，结果直接写进界面 |
| 抓取超时 / 403 | 记成该来源的"不可用"，继续其余来源，不整单失败 |

## 十一、测试

- **纯函数**：事实清单校验 / 出处核对 / ST 格式组装（不联网）
- **路由**：提交 + 轮询的状态机（起 → 跑 → 成 / 败）
- **端到端一条**：dev 宿主里用假检索喂进去（不真联网）
- 沿用现有 53 个检查器的纪律：**断言跟随设计变更**，检查器要先证明咬得动

## 十二、来源范围的现实（已定，不再挂“未决”）

（域名逐条实测见**第六节**，这里只说结论。）

代理：环境变量无；宿主设置里也没搜到 proxy 配置（没有证据支持有代理）
→ 按**直连**处理。

**结论（v1 范围，必须写清）：**

- 白名单路 = **萌娘百科 + arXiv** 两个源；覆盖 ACGN / 游戏设定 与 学术题材。
- 历史 / 地理 / 真实人物这类题材（维基在墙内不通）**只能走兜底**：
  由 Agent 检索后喂进来。这不是降级方案，而是这个网络环境下的唯一路。
- 检索实现：v1 只做这两个站（各自的搜索页 + 正文抓取），每站摸一次接口；
  其余站先在名单里留名，靠“来源可用性检查”标出不通。
- 白名单里还留着维基 / Fandom 的名字（标注“需代理”），
  因为它们不是“不该用”，而是“这台机上暂时到不了”。
